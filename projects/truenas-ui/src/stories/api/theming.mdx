# Theming in TrueNAS UI Library

This library provides a centralized theme system with multiple built-in themes. You can switch themes using the **Storybook toolbar** or programmatically via the **TnThemeService**.

## Available Themes
- **TN Dark** (default)
- **TN Blue**
- **Dracula**
- **Nord**
- **Paper**
- **Solarized Dark**
- **Midnight**
- **High Contrast**

## TnThemeService API

The `TnThemeService` is a signal-based theme orchestration service that manages theme state, DOM updates, and localStorage persistence.

### Basic Usage

```typescript
import { Component, inject, effect } from '@angular/core';
import { TnThemeService, TnTheme } from '@truenas/ui-components';

@Component({
  selector: 'app-theme-switcher',
  template: `
    <select (change)="onThemeChange($event)">
      @for (theme of themes; track theme.name) {
        <option [value]="theme.name">{{ theme.label }}</option>
      }
    </select>
  `
})
export class ThemeSwitcherComponent {
  private themeService = inject(TnThemeService);

  // Get all available themes
  themes = this.themeService.availableThemes;

  // React to theme changes
  constructor() {
    effect(() => {
      const current = this.themeService.currentTheme();
      console.log('Theme changed to:', current?.label);
    });
  }

  onThemeChange(event: Event): void {
    const themeName = (event.target as HTMLSelectElement).value as TnTheme;
    this.themeService.setTheme(themeName);
  }
}
```

### API Reference

#### Properties

- **`currentTheme`**: `Signal<TnThemeDefinition | undefined>` - Reactive signal containing the current theme definition
- **`currentThemeClass`**: `Signal<string>` - Reactive signal containing the current theme's CSS class name
- **`availableThemes`**: `readonly TnThemeDefinition[]` - Array of all available theme definitions

#### Methods

- **`setTheme(theme: TnTheme): boolean`** - Sets the active theme. Returns `true` if successful, `false` if theme not found
- **`getCurrentTheme(): TnTheme`** - Returns the current theme enum value
- **`resetToDefault(): void`** - Resets to the default theme (TN Dark)
- **`hasTheme(theme: TnTheme): boolean`** - Checks if a theme exists

### Type-Safe Theme Enum

Use the `TnTheme` enum for type-safe theme selection:

```typescript
import { TnTheme } from '@truenas/ui-components';

// ✅ Type-safe with autocomplete
themeService.setTheme(TnTheme.Dracula);
themeService.setTheme(TnTheme.Nord);

// ❌ Avoid hardcoded strings
themeService.setTheme('tn-dracula'); // This works but no type safety
```

### Theme Definitions

Each `TnThemeDefinition` contains:

```typescript
interface TnThemeDefinition {
  name: TnTheme;           // Enum value (e.g., TnTheme.Dracula)
  label: string;           // Display name (e.g., "Dracula")
  className: string;       // CSS class (e.g., "tn-dracula")
  description?: string;    // Optional description
}
```

### Features

- **Signal-based reactivity** - Use Angular signals for reactive theme state
- **LocalStorage persistence** - Theme preference automatically saved to `localStorage` with key `tn-theme`
- **Automatic DOM updates** - CSS class automatically applied to `<html>` element
- **SSR-safe** - Platform checks ensure browser-only code doesn't run on server
- **Type-safe API** - Use `TnTheme` enum instead of string literals

## Usage in Components
Use CSS variables to apply theme styles:

```scss
.my-component {
  background-color: var(--tn-bg1);
  color: var(--tn-fg1);
  border: 1px solid var(--tn-lines);
}
```

## Theme Variables Reference

Each theme defines the following CSS custom properties:

### Core Colors
- `--tn-primary`: Primary brand color
- `--tn-primary-txt`: Text color for primary backgrounds
- `--tn-accent`: Accent color for highlights
- `--tn-accent-txt`: Text color for accent backgrounds
- `--tn-topbar`: Top navigation bar background
- `--tn-topbar-txt`: Top navigation bar text
- `--tn-topbar-hover`: The bar under the pointer — what `tn-table` fills a hovered sortable header with. Every palette declares its own, shifted off that palette's own `--tn-topbar`; see the note at the token in `themes.css` for why one derivation could not serve all nine

### Background Colors
- `--tn-bg1`: Main background color
- `--tn-bg2`: Secondary background color (cards, panels)
- `--tn-bg3`: Tertiary background color (elevated surfaces, popovers)
- `--tn-alt-bg1`: Alternative background 1 (hover, selected states)
- `--tn-alt-bg2`: Alternative background 2 (skeleton loaders, subtle separators)

### Text Colors
- `--tn-fg1`: Primary text color (headings, body)
- `--tn-fg2`: Secondary text color (labels, descriptions)
- `--tn-alt-fg1`: Muted text (placeholders, group labels, breadcrumb separators)
- `--tn-alt-fg2`: Alternative text color 2

`--tn-fg1`, `--tn-fg2` and `--tn-alt-fg1` each clear the 4.5:1 text minimum (WCAG 1.4.3) against `--tn-bg1` and `--tn-bg2` in every theme, and `--tn-fg1` reads at least as well as `--tn-fg2` in all nine. A palette is free to invert that pair — `text-fg-contrast.spec.ts` records rather than forbids it — and `.tn-midnight` did, until #282 lifted its `--tn-fg1` to clear AA on the fills above `--tn-bg2`. That is the whole of the token-level guarantee: it says nothing about `--tn-bg3`, either `--tn-alt-bg`, or either `--tn-topbar` surface. `--tn-alt-fg2` has no page-surface guarantee at all; it is drawn on the `--tn-alt-bg` surfaces rather than on the page. `text-fg-contrast.spec.ts` holds all nine palettes to what is claimed here.

#### Which surfaces the text guarantee covers

| surface | covered by the token guarantee | measured where |
|---|---|---|
| `--tn-bg1`, `--tn-bg2` | yes, for `--tn-fg1`, `--tn-fg2` and `--tn-alt-fg1` in all nine palettes | `text-fg-contrast.spec.ts` |
| `--tn-bg3`, `--tn-alt-bg1`, `--tn-alt-bg2` | **no** — a token that clears 4.5:1 on the page is not promised on a fill above it | `text-token-surface-contrast.spec.ts`, per pairing |
| `--tn-topbar` | **no** — the bar has its own label token, `--tn-topbar-txt`, which is guaranteed 4.5:1 on it in every palette | `text-token-surface-contrast.spec.ts` |
| `--tn-topbar-hover` | **no** — it carries the same `--tn-topbar-txt`, and is guaranteed 4.5:1 under it in every palette for the same reason | `text-token-surface-contrast.spec.ts`, which measures all nine (6.16–11.93:1) |

The distinction is between a *token* and a *pairing*. No text token is promised on the three fills above the page, so a component that starts drawing one there is making a claim nothing has tuned for. What is checked instead is every pairing this library actually paints: `text-token-surface-contrast.spec.ts` lists them with their call sites, measures each in all nine palettes, and fails when a stylesheet grows a new fill or a new text colour without the list being updated. Every token pairing on those fills clears AA today, and nothing is recorded there as a known gap. Three did not, and each was fixed by moving a token rather than the fill, because the fill was the thing carrying the elevation cue: `.tn-midnight` drew `--tn-fg1` at 3.19–3.91:1 on its three fills until #282, `.tn-solarized-dark` drew `--tn-alt-fg1` at 3.79:1 on `--tn-alt-bg1`, where `tn-stepper` puts its step indicator, until #283, and the sortable table header's hover left its label at 3.54–3.92:1 in the four palettes with mid-tone bars until #284.

That last one is the case for a token rather than a derived fill, and it is worth reading before deriving a surface anywhere else. The hover was `color-mix(in srgb, var(--tn-topbar) 85%, var(--tn-topbar-txt))` — the bar moved toward its own label. Every palette's label is lighter than its bar, so that moved the surface toward the text and the label's ratio could only fall; it started at 4.58–5.01:1 on the four mid-tone bars and landed at 3.54–3.92:1. No percentage rescues those four: the two constraints pull opposite ways under this derivation — more label mixed in is a more visible hover and a less legible label — and on all four the label is still short of 4.5:1 at 95%, where the hover has already faded to 1.1:1 against the bar. Nor is there a single direction to move a bar in, which is the other half of it: a near-black bar can only be lightened to show anything at all, and lightening is exactly what breaks a mid-tone one. So `--tn-topbar-hover` is declared per palette, each value a hue-preserving lightness shift of that palette's own bar, and `text-token-surface-contrast.spec.ts` holds all nine to two separate things — the label at 4.5:1 on the fill, and the fill far enough off the bar (1.30:1) to be an affordance at all. The second is not implied by the first: a hover equal to the bar would pass every contrast case in the file and paint nothing.

**Writing a component:** text on `--tn-bg1` or `--tn-bg2` can read the text tokens freely. Text on any other surface has to be measured against that surface — add the pairing to `text-token-surface-contrast.spec.ts`, which is what turns "measure it there" into something that runs.

### Non-Text Foregrounds
- `--tn-fg3`: De-emphasized non-text foreground (icon and glyph strokes, decorative marks)
- `--tn-fg4`: The most subdued foreground (inactive affordances, decorative marks)

`--tn-fg3` and `--tn-fg4` are **not text colors**, despite sitting in the same numeric ramp as `--tn-fg1` and `--tn-fg2`. Each is tuned to the 3:1 UI-component/graphical-object minimum (WCAG 1.4.11) against `--tn-bg1` and `--tn-bg2` in every theme, and to nothing on any other surface. Neither is guaranteed as text in any theme, and neither is meant to be: `--tn-fg4` reaches the 4.5:1 text minimum (WCAG 1.4.3) in none of the nine and `--tn-fg3` in only four, so a call site that relied on either would be relying on the theme it happened to be written against. A muted value that clears 4.5:1 on a light surface is a value you cannot tell apart from `--tn-fg2`, which is what the muted step exists to be distinct from. For muted text — placeholders, timestamps, hints — use `--tn-alt-fg1`, which is tuned for it and clears 4.5:1 against `--tn-bg1` and `--tn-bg2` in every theme. It did not always: when `--tn-fg3` and `--tn-fg4` were moved out of the text roles, `.tn-solarized-dark` measured `--tn-alt-fg1` at 4.11:1 on `--tn-bg2`, along with that theme's `--tn-fg1` (2.79:1 on `--tn-bg1`) and `--tn-fg2` (4.32:1 on `--tn-bg2`), so the muted role was pointed at a token that failed there too. All three were retuned to Solarized's own lighter tones (#265). `--tn-alt-fg1` has since left that ramp (#283): the tones in it that clear 4.5:1 on `--tn-alt-bg1`, where `tn-stepper` draws the step indicator, are the two the theme has already spent on `--tn-alt-fg2` and `--tn-fg1`, so a muted token taken from the ramp would be one of those under a second name.

### UI Elements
- `--tn-lines`: Border and divider color
- `--tn-btn-default-bg`: Default button background
- `--tn-btn-default-txt`: Default button text

### Status Colors
- `--tn-red`: Error/danger color
- `--tn-green`: Success color
- `--tn-yellow`: Warning color
- `--tn-blue`: Info color
- `--tn-orange`: Secondary warning
- `--tn-cyan`: Info accent

`--tn-red` is tuned toward the 3:1 UI-component/border minimum (WCAG 1.4.11) in most themes but not all — `.tn-high-contrast`'s `--tn-red` measures 2.94:1 against `--tn-bg1` — and it is not tuned for the 4.5:1 text minimum (WCAG 1.4.3). The other status colors are not tuned toward either threshold. None of the six is a text color. For text — validation messages, inline errors, banner headings, toast and card status labels, the required asterisk — and for the borders and icons drawn alongside it, use one of the five text-safe status tokens below instead.

#### Which status tokens a custom theme must declare

**All five, explicitly.** For the four semantic tokens, each theme's value is a hue-preserving lightness shift of that same theme's own hue token — the smallest step that clears 4.5:1 on every surface in its row. That step is a measurement against your own backgrounds, so only your palette can supply it and no default can stand in for it.

| token | drawn as | guaranteed 4.5:1 against | derived from | measured by |
|---|---|---|---|---|
| `--tn-error-text` | error and validation text on the page and on cards | `--tn-bg1`, `--tn-bg2` | `--tn-red` | `error-text-contrast.spec.ts` |
| `--tn-info` | info status text, borders and icons | `--tn-alt-bg1`, `--tn-bg1`, `--tn-bg2` | `--tn-blue` | `semantic-status-contrast.spec.ts` |
| `--tn-warning` | warning status text, borders and icons | `--tn-alt-bg1`, `--tn-bg1`, `--tn-bg2` | `--tn-orange` | `semantic-status-contrast.spec.ts` |
| `--tn-error` | error status text, borders and icons | `--tn-alt-bg1`, `--tn-bg1`, `--tn-bg2` | `--tn-red` | `semantic-status-contrast.spec.ts` |
| `--tn-success` | success status text, borders and icons | `--tn-alt-bg1`, `--tn-bg1`, `--tn-bg2` | `--tn-green` | `semantic-status-contrast.spec.ts` |

Those are the surfaces this library paints a status color on: `--tn-alt-bg1` is `tn-banner`'s fill, `--tn-bg1` the page and the file-picker popup, `--tn-bg2` the card and the toast. As with the text tokens above, the covered list is the whole of the guarantee — `--tn-bg3`, `--tn-alt-bg2` and both `--tn-topbar` surfaces appear in no row, so a status color drawn on one of those is a pairing nothing has tuned for, and it belongs in `text-token-surface-contrast.spec.ts` with a measurement.

`--tn-error` is **not** `--tn-error-text`, and what separates them is which surfaces each was measured on rather than a shade of red. `--tn-error-text` is `--tn-red`'s companion and covers the two page surfaces only; in the default theme it measures 3.64:1 on `--tn-alt-bg1`, so it is the wrong token inside a banner. `--tn-error`'s row covers that surface as well, which makes it a superset: reading it on the page or on a card loses nothing, and `form-errors`, `form-field` and `select` already paint page-surface error text from it. What does not work is the other direction — `--tn-error-text` inside a banner — or either of them on a surface that appears in neither row.

#### Omitting one is silent, not loud

Omitting one does not leave the property unset, and it does not reach the fallback chain either. `:root` declares all five itself, so there is always a value to inherit. A theme class is applied to the same root element and has the same specificity as `:root`, so a theme class that declares the property wins by source order — but one that omits it declares nothing to compete with `:root` at all, and `:root`'s value is what applies. Which value that is depends on the form `:root` used, and the five are not alike:

- `--tn-error-text`, `--tn-info` and `--tn-error` are literals there — `#de6d6d`, `#00adf8`, `#e78888`, the same values `.tn-dark` declares. Omit one and your theme paints the default theme's color on your own surfaces, which in a light theme is a color that was chosen for a dark one.
- `--tn-warning` and `--tn-success` are `var(--tn-orange)` and `var(--tn-green)` there. A `var()` inside a custom property is substituted on the element the property is computed on, which is the same root element your theme class sits on — so these two do resolve to *your* `--tn-orange` and `--tn-green`. That is the untuned hue token, which is what the semantic token exists to replace: `.tn-dark` clears 4.5:1 on all three surfaces with its own orange and green, and nothing promises yours does.

Either way the result is a color nobody measured against your backgrounds, and either way nothing in the cascade reports it. Inside this repo `itDeclares` in `palette-contrast-testing.ts` is what does: it fails a palette that inherits one of these rather than resolving the inherited value and reporting a ratio that was true of a different theme. A consumer theme is outside that spec's reach, which is why the requirement is written here — and why it is all five rather than only the three with a literal behind them.

#### What the fallback chain is for

Every reader spells the chain whole — `var(--tn-error, var(--tn-red, #bd2626))`, and the matching shape for the other four. It is not a safety net for a theme that omits the token, for the reason just given; it is reached only when no theme stylesheet is loaded at all, and its two links serve two different readers:

- The **middle link** is the hue token, so a consumer stylesheet that predates these five but defines the TrueNAS palette keeps its own branding instead of having it discarded for a literal. That link is not tuned for text, and reaching it is the trade being made: in the default theme `--tn-red` measures 3.15:1 on `--tn-bg1` and 2.22:1 on `--tn-alt-bg1`, and `--tn-blue` 2.56:1 on `--tn-alt-bg1`.
- The **terminal literal** is reachable only with no theme stylesheet at all, where the surface is the browser's own white. For the four semantic tokens it is `.tn-blue`'s value for that token — `#006997`, `#955313`, `#bd2626`, `#416f26` — a light theme's color being the right one on white; `--tn-error-text`'s is `#b91c1c`, at 6.47:1. All five clear 4.5:1 there, and the specs in the table above assert it.

A palette may declare one of the five as a plain alias of its hue token where that hue already clears every surface in its row, and five of the nine do: `--tn-warning` and `--tn-success` in `:root`, `.tn-dark` and `.tn-dracula`, `--tn-info` in `.tn-paper`, and `--tn-error-text` in `.tn-blue` and `.tn-dracula`. That is a measurement per palette rather than a shortcut to copy — the other four declare all five as their own shade, and `.tn-high-contrast` needs `#ad000d` for `--tn-error` where its `--tn-red` is `#ff0013`.

**Writing a component:** read the token tuned for the surface you are painting, and spell the chain whole. A component that paints a fill of its own *and* accepts projected content has one more job: a control a caller projects into it reads the tokens *it* was written against, and two of those are tuned for `--tn-bg1` and `--tn-bg2` and for nothing above them. Rebind each one for the whole fill rather than for one slot of it, so that every slot a caller can reach is covered by the same guarantee.

**The rule covers exactly these two** — every token tuned only for `--tn-bg1`/`--tn-bg2` that a projected control can read:

| token | who reads it | on `--tn-alt-bg1` | rebind to |
|---|---|---|---|
| `--tn-error-text` | `tn-checkbox` and `tn-radio` error text, `.button-outline-warn`'s label | 3.43:1 worst of nine (`.tn-dracula`), fails AA in six | `--tn-error`, tuned for this fill and still red — 4.62:1 worst |
| `--tn-primary-text` | `.button-outline-primary`'s label, and `tn-form-field`'s **focused** label | 3.49:1 worst of nine (`.tn-dracula`), fails AA in the same six | `--tn-fg1` — 6.24:1 worst |

The five text tokens are **not** in this class, and that is the distinction worth keeping: `--tn-fg1`, `--tn-fg2`, `--tn-alt-fg1`, `--tn-alt-fg2` and `--tn-topbar-txt` are held per *pairing* by `text-token-surface-contrast.spec.ts`, which measures every pairing this library paints and records none as a gap today. A token with a measured pairing on your fill needs no rebind — the measurement is what the rebind would be for.

`--tn-primary-text` goes to `--tn-fg1` rather than to a tuned accent because **there is no accent tuned for a fill above the page.** `--tn-primary` is worse there (1.82:1 worst), and the four semantic tokens that do clear `--tn-alt-bg1` carry a status meaning — "info", "warning" — that a primary action or a focus cue does not have. So a projected label stops being accent-coloured on your fill instead of being illegible in six themes.

**Be precise about what that costs for a focused field, because it is more than a hue.** `tn-form-field`'s label is already `--tn-fg1` at rest, so rebinding its focused colour to the same token makes the two identical — on your fill that cue is not recoloured, it is gone. It was a redundant secondary one: `.tn-input-container:focus-within` still draws a `--tn-primary` border and a 2px ring, so SC 2.4.7 holds on the control itself, and an outline button keeps its `--tn-primary` border. A cue that is absent beats one that is present and unreadable in six of the nine palettes — and restoring it properly needs an accent tuned for the fill, which is the same palette decision the `--tn-alt-bg2` paragraph below describes.

**On `--tn-alt-bg2` the error half of this rule has no answer yet.** Every semantic token fails AA on that fill — `--tn-error` 2.98:1, `--tn-info` 3.00:1, `--tn-warning` 2.97:1, `--tn-success` 3.33:1, worst of nine — where every one of them clears `--tn-alt-bg1`. The colours that do clear it are the text tokens `--tn-fg1` (5.62:1 worst of nine) and `--tn-fg2`, whose pairings on that fill `text-token-surface-contrast.spec.ts` already measures in all nine — and rebinding error text to either discards the red, which is the status rather than decoration. Retuning a token or moving that fill is a decision about how a theme looks, so the components filling `--tn-alt-bg2` under a projection slot are recorded in `projected-token-rebind.spec.ts` as pending a decision rather than rebound to something that loses meaning.

`projected-token-rebind.spec.ts` is what makes this rule run: it fails when a component that fills an untuned surface and accepts projected content carries no rebind, and when a rebind is scoped to a *descendant* of the element painting the fill — which is the mistake this paragraph warns against and which no other spec can see, because `PAINTS_UNTUNED`'s detector matches a literal `color:` and a custom property is invisible to it.

## Implementation Notes

### Component Integration
Components should use the `--lines` variable for borders and dividers:

```scss
.component {
  border: 1px solid var(--tn-lines);
  border-bottom: 1px solid var(--tn-lines);
}
```

### Fallback Values
When using CSS variables, always provide fallback values for better compatibility:

```scss
.component {
  background-color: var(--tn-bg1, #1E1E1E);
  color: var(--tn-fg1, #ffffff);
  border: 1px solid var(--tn-lines, #383838);
}
```
